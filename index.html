Pattern B — one persistent process

Cold start is paid once, up front. The guardrail stages become cheap warm follow-up messages. Same time axis as above.

The main problem is not cold start — it is the guardrail's time-to-first-token

Consolidating three processes into one warm process cuts the turn roughly in half (– → –). But only about – of that saving comes from paying the ~2 s Node cold start once instead of three times.

The bigger loss in Pattern A is that each guardrail runs as a full cold inference: the haiku input guardrail spends – just reaching its first token (thinking + a fresh, un-cached system prompt on every spawn) for what is a one-word verdict. In Pattern B the same check, sent into an already-warm context, reaches first token in – and generates in well under a second.

The main agent's generation (–) is the irreducible core in both — it is real answer tokens. Attack the guardrail overhead, not the answer.

Method & honest caveats

  • Harness: standalone Python, spawns the real claude CLI v2.1.212. Cold start = wall time from Process.Start to the CLI's system/init event; time-to-first-token and generation come from the CLI's own result event (ttft_ms, duration_ms). The app's own code was not modified.
  • Faithful to the app in flags, models and prompts (copied from ChatbotPrompts.cs / ClaudeCliClient.cs / ClaudeSession.cs).
  • Not apples-to-apples on the guardrail model. Pattern A runs the guardrails on haiku with --json-schema (as shipped). Pattern B cannot switch model or schema per message inside one process, so its guardrail stages run on sonnet with the instruction inline — yet they are still far faster, because the context is warm. This strengthens, not weakens, the conclusion.
  • Main agent is tool-less (no MCP server was stood up). Real turns that call HCM tools add API round-trips on top of both patterns equally.
  • N = 5 (credits were limited). Time-to-first-token is high-variance; treat the shape, not the third digit, as the finding.
